# Retry a rejected push in-attempt instead of waiting a pull interval

<summary>
- A push rejected because the remote moved is retried immediately, inside the same operation
- Retries are bounded to three attempts total and separated by 100–500 ms of random jitter
- Every push that can lose a race uses one shared helper, so the sites cannot drift apart
- Rejections that are not a race — auth, ruleset, network — are not retried and surface exactly as before
- Each retry is visible in the log and counted in a new Prometheus counter
- API callers stop receiving 500s for a lost push race
</summary>

<objective>
Make a lost push race converge inside the operation that hit it. Today the remote moves between fetch and push, git rejects with `fetch first`, and git-rest returns the error and waits a full pull interval before trying again — so on a contended branch the loser stays behind indefinitely. Retrying in-attempt costs a few hundred milliseconds and removes that lag.
</objective>

<context>
Read `pkg/git/git.go`. The plain `git push` sites that can lose a race are, by enclosing function:

- `writeFileLocked` — `if g.hasRemote(ctx) { if err := g.runCmd(ctx, g.repoPath, "push"); err != nil {` (the `write_file` failure that surfaces as `500 … write file: git push:`; both `WriteFile` and `WriteFileIfAbsent` reach it)
- `DeleteFile` — the same shape for `delete_file`
- `pullMergeAndPush` — the push after a clean merge, wrapped `"push after clean merge failed"`
- `commitAndPushMerge` (reached from `resolveConflictMerge` via `resolveConflictPaths`) — the push after a resolved merge, wrapped `"push after resolved merge failed"`
- `syncWithUpstream` — the `remoteSHA == baseSHA` branch, wrapped `"push failed"`

Three pushes are deliberately OUT of scope: `pullRebaseAndPush` is marked `nolint:unused` and is not called from `Pull`; `rescueDirtyTree` pushes a unique `rescue/<timestamp>` ref that no other writer contends for; and `syncOnStartup` in `main.go` is a best-effort boot-time push that warn-logs and defers to the next API write, which this change makes converge in-attempt.

Read `pkg/metrics/metrics.go` for the counter conventions: every series is declared as a package var, registered in `init()`, and pre-initialised with an explicit `.Add(0)`. `PullRescuesTotal` is the closest exemplar — copy its shape.

Read `pkg/git/git_suite_test.go`, `pkg/git/git_test.go` and `pkg/git/resolve_conflict_merge_test.go` for the Ginkgo v2 / Gomega conventions, the real-temp-repo test helpers (`initRepo`), and the two hand-written metrics doubles.

Read `runCmd` and `runCmdRaw` in `pkg/git/git.go` before choosing which to call: `runCmdRaw` returns git's combined output, which is what the rejection classifier needs.

The coding guide `go-context-cancellation-in-loops` governs the retry loop — check `ctx.Done()` at the top of each iteration and wrap with `ctx.Err()`. The coding guide `go-prometheus-metrics-guide` covers the counter declaration/registration shape.

Three values are deliberate and not configurable: 3 total attempts, 100–500 ms jitter, and the counter name. They are core behaviour, not tunables — do not add a config field, flag, or env var for any of them.

`pushWithRetry` runs inside `writeFileLocked`, `DeleteFile` and `Pull`, all of which hold `g.mu`. Two retries can therefore hold that mutex for up to about a second, serialising concurrent reads. That is accepted: the hold is bounded, and the deployment is a single writer replica.
</context>

2. Add a helper in `pkg/git/git.go`:

   `func (g *git) pushWithRetry(ctx context.Context, upstream string) error` — `upstream` may be empty; when it is, resolve `@{u}` on the retry path only, before the `git fetch`.

   Contract:
   - Attempt the push with `g.runCmdRaw(ctx, g.repoPath, "push")`. Success on the first attempt must behave exactly as today — no extra commands, no log line, no counter increment.
   - Classify a failure as **retryable** only when git's combined output contains `[rejected]` together with either `(fetch first)` or `(non-fast-forward)`. Everything else — auth failure, ruleset refusal, network error, missing remote — is **terminal**. On a terminal failure return `errors.Wrapf(ctx, err, "git %v: %s", args, out)` with `args := []string{"push"}` and `out` the combined output, so the text matches what `runCmd` produces today byte for byte.
   - Extract the classification into a pure function over git's combined output, so it can be table-tested and so `pushWithRetry` stays inside the `funlen` (80 lines / 50 statements) and `nestif` (4) budgets in `.golangci.yml`.
   - On a retryable failure, before each retry: sleep 100–500 ms of random jitter (`math/rand/v2`, annotated `//nolint:gosec // jitter, not security-sensitive` — gosec G404 covers it), then `g.runCmd(ctx, g.repoPath, "fetch")`, then `g.runCmdRaw(ctx, g.repoPath, "merge", "--no-edit", <upstream>)` into `mergeOut`. If that merge fails, run `git merge --abort`, stop retrying, and return the merge error wrapped as `errors.Wrapf(ctx, mergeErr, "merge %s: %s", upstream, mergeOut)` — the conflict machinery belongs to the pull path, and a half-finished merge must not be left in the tree. If the `fetch` itself fails, stop retrying and return it wrapped as `errors.Wrapf(ctx, fetchErr, "fetch before push retry")`.
   - Bound the total attempts at 3 (two retries). Never exceed it.
   - Check `ctx.Done()` at the top of each retry iteration and inside the jitter sleep (`select` on `ctx.Done()` and a timer). On cancellation return `errors.Wrap(ctx, ctx.Err(), …)`.
   - Log on each retry: `slog.InfoContext(ctx, "git-rest: push retry", "attempt", n, "max", 3)`. On the first success after at least one retry, log `slog.InfoContext(ctx, "git-rest: push succeeded after retry", "attempt", n, "sha", <HEAD sha>)` — read the sha with `git rev-parse HEAD`. Both messages must contain the literal substrings `push retry` and `push succeeded after retry`.
   - Call `g.metrics.IncPushRetry()` once per retry performed, never on the first attempt.
